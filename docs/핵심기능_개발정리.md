## 1. 공통 기반 (모든 기능의 전제)

### 1-1. 아키텍처
```
[차량 A 앱] ─┐                                ┌─ [차량 B 앱]
             ├── Firebase Realtime DB ─────────┤
[가상 차량 봇]┘   방·멤버 상태·제안·음성(base64)    └─ [차량 C 앱]
 (맥 스크립트, REST)
     │
  Pleos SDK (NaviHelper / Vehicle / FusedLocation / STT / TTS)
```
- **차량 간 통신은 SDK에 없음** → 자체 서버 필수. **Firebase Realtime DB로 확정** (검증 결과 1-6). 데이터 구조는 9-1.
- 시연은 **에뮬레이터 1대(내 차) + 가상 차량 2~3대(봇)** 구성. 봇은 맥에서 스크립트로 Realtime DB REST에 직접 씀(9-3). 에뮬레이터 2대는 성능상 무리.
- **FCM(푸시) 사용 안 함**: Play 서비스가 없어 불가. 앱을 FGS로 유지하고 실시간 리스너로 수신.
- **AWS(EC2·RDS) 불필요**: 추천 점수는 제안하는 차량의 앱이 계산. 서비스가 커지면 Cloud Functions로 확장.

### 1-3. 에뮬레이터 한계 (시연 설계에 반영)
| 한계 | 원인 | 대응 |
|---|---|---|
| 내비 현재 위치가 판교(소프트웨어드림센터)에 고정 | 에뮬 GPS가 NMEA 체크섬을 `*47`로 고정 → 내비가 전부 거부. 코드로 내비 위치 변경 API 없음 | **시연 스토리를 "판교 출발"로 구성**. 우리 앱의 내 차 위치는 FusedLocation(`adb emu geo fix` / `tools/nmea_drive.py`)으로 이동 |
| 내비 지도 배경 없음 | 에뮬 전용 빈 스타일(`connect_empty`: 배경+해안선만) | 최종 와이어프레임은 지도 없이 카드·진행 바 중심이라 필수 아님. 자체 그룹 지도는 선택 — ❓ AAOS 동작 미검증 |
| 내비 남은 시간이 줄지 않음 | 위치 고정 | 가상 차량 변화 중심으로 장면 구성 |
| 차량이 EV 설정 | 연료 API 미지원 | 내연기관 분기 로직은 코드로만 구현, "주유 필요"는 봇으로 시연 |
| Virtual Console에 위치·연료 항목 없음 | 콘솔 설계 | 배터리·기어·속도·경고등만 콘솔로 조작 |
| 비행기 모드를 켰다 끄면 네트워크가 복구되지 않음 | `eth0`가 꺼진 채로 남고 adb root 불가 | 재부팅으로 복구. 끊김 테스트는 SDK `goOffline`/`goOnline` 사용 |
| Google Play 서비스 없음 | 에뮬 이미지에 gms·gsf·Play 스토어 미설치 | Firebase는 동작(1-6). FCM 등 Play 서비스 의존 기능만 사용 불가 |

### 1-4. Virtual Console (시연 자동화 도구)
- `adb forward tcp:8088 tcp:8088` → 브라우저 `http://127.0.0.1:8088`
- HTTP로도 조작 가능(시연 스크립트용, 페이지 열린 상태 또는 `POST /browser/session` 하트비트 필요):
  - `PUT /vehicle/gear?gear=Drive` · `PUT /vehicle/controls?speed=60&accelerator=20&brake=0&steering=0`
  - `PUT /vehicle/ev-battery?field=soc&value=15` · `PUT /vehicle/lights?feature=hazard&value=true`

- **보안 규칙**: 지금은 테스트 모드(열려 있음). 테스트 단계라 그대로 두고, 초안 `firebase/database.rules.json`(방 멤버만 읽기, 자기 uid 경로에만 쓰기, 참여 코드 확인, 음성 크기 제한)은 아직 적용·시험 안 함. 적용하면 봇도 익명 uid로 멤버 등록이 필요.

### 1-7. FGS·백그라운드 수신 검증 결과 (에뮬 실측)
**방법**: 앱이 Realtime DB `rooms/spike/members`를 구독 → 다른 앱(`com.test.naviratio`)을 띄워 우리 앱 창을 밀어내 백그라운드로 보냄 → 맥에서 REST로 값을 쓰고 수신 지연 측정

| 경우 | 앱 상태 | 결과 |
|---|---|---|
| A. FGS 없음 | `cached`, `isFrozen=true` | ❌ 30초 동안 수신 없음. 앱을 다시 띄우자 그때 도착(**지연 35초**) |
| B. FGS `specialUse` | `isFrozen=false` | ✅ 0.7~1.0초. **2분 30초 대기 후에도** 0.75초 (유휴 끊김 없음) |
| C1. FGS `location`, 위치 권한 없음 | — | ❌ 시작 실패 `SecurityException: Starting FGS with type location … requires permissions … ACCESS_COARSE_LOCATION, ACCESS_FINE_LOCATION` |
| C2. FGS `location`, 위치 권한 있음 | `isFrozen=false` | ✅ 0.7~0.8초 |
| D. FGS 켠 채 프로세스 강제 종료(`am crash`) | 서비스 재시작됨 | ⚠️ 시스템이 서비스를 다시 살려 `location` 유형 FGS로 유지, 얼지 않음. 단 서비스 시작 로그가 찍히지 않아 재시작 경로는 완전히 확인 못 함 |

**새로 알게 된 것**
- **Home 버튼은 앱을 백그라운드로 보내지 않음**: Pleos에서는 Home을 눌러도 우리 앱이 창에 그대로 보이고 포그라운드 유지. **다른 앱이 우리 창을 차지할 때만** 백그라운드·동결됨.
- **앱은 user 10(운전자 프로필)에서 실행됨**: `pm grant`를 사용자 지정 없이 실행하면 user 0에만 적용되어 FGS 시작 실패. 테스트 시 `adb shell pm grant --user 10 com.spike.pleos android.permission.ACCESS_FINE_LOCATION`.

**설계 반영**
- FGS 유형은 **`location`으로 확정** (manifest `foregroundServiceType="location"`, 권한 `FOREGROUND_SERVICE_LOCATION` + `ACCESS_FINE_LOCATION`/`ACCESS_COARSE_LOCATION`).
- 순서: **방 참여 전, 앱이 화면에 떠 있을 때 위치 권한 요청 → 허용 후 FGS 시작**. 거부 시 FGS를 시작할 수 없으므로 "위치 공유 없이는 그룹 주행 불가" 안내.
- Firebase 연결·리스너는 Activity가 아니라 **서비스 안에서 시작** (프로세스 재시작 시 서비스만 살아나므로 수신도 함께 복구되도록). 현재 스파이크 앱은 Activity에서 시작함.
- 프로세스가 완전히 종료되면 깨울 방법이 없음(FCM 불가). "여행 진행 중에는 FGS로 유지, 종료 시 수신 안 함"으로 명시.

**구현 중 확인** (별도 검증 불필요, 실제 앱을 만들면서 자연스럽게 확인)
- [x] 위치 권한 요청 팝업: ✅ 정차(P단) 중에는 표준 팝업이 정상 표시(위치 → 알림 순). ⚠️ **주행 중(D·100km/h)에는 팝업 대신 "주행 중에는 사용할 수 없습니다" 화면이 뜨고, 권한 결과 콜백이 곧바로 거부로 옴** → P단이 되면 팝업이 다시 떠서 허용 시 콜백이 한 번 더 옴 (11/15 실측). 권한 요청은 정차 중에 하는 것을 전제로 한다
- [x] FGS 동결 방지: ✅ 갈래 앱에서 재확인. 다른 앱이 창을 차지해 `visible=false`여도 `isFrozen=false` (11/15)
- ⚠️ **Back 키: 기본 동작으로는 아무 변화 없음** — Activity가 종료되지 않고 창에 그대로 남음(Android 12+ 루트 Activity의 Back은 종료 대신 태스크를 뒤로 보내는데, Pleos 분할 창에서는 그대로 보임). 종료하려면 Back을 직접 처리하거나 메뉴에 종료 버튼이 필요 (11/15 실측)
- [ ] 프로세스 재시작 후 수신: 데모·PT에서는 거의 발생하지 않음(실차 안정성 문제). 검증 대신 **Firebase 연결을 서비스에서 시작**하는 구현 원칙으로 대응

## 3. 기본 기능 A — 차량별 상태 공유 (멤버 카드)

### 구현 방식
각 차량 앱이 아래 값을 서버(`members/{uid}`, 9-1)에 올리고(위치 10초, 상태 변화는 즉시), 다른 차량은 구독해서 멤버 카드에 표시.

| 표시 항목 | 데이터 출처 | 상태 |
|---|---|---|
| 도착 예정 시각 / 남은 거리 | NaviHelper `getDestinationInfo` → `remainTime`(초), `remainDistance`(m) | ✅ |
| 목적지 이름·좌표 | NaviHelper `DestinationInfo` | ✅ |
| 경유지 이름·남은 시간 | NaviHelper `onWayPointInfo` / `DrivingInfo` | ✅ (좌표는 0.0 → 5-0) |
| 현재 위치 좌표 | FusedLocation `registerFusedLocationCallback` | ✅ (내비 위치와 별개) |
| 위치 문구("영동고속도로 · 원주 부근") | ❓ 내비 `DrivingInfo`에 현재 도로명이 있는지 확인 필요. 없으면 카카오 로컬 `coord2regioncode`로 시·군 이름만 ("원주 부근") | ❓ |
| 정차 장소 이름("○○마트 강릉점") | 목적지·경유지 반경 안이면 그 이름, 아니면 위치 문구로 대체 | 자체 로직 |
| 이동중 / 정차중 | AAOS `PERF_VEHICLE_SPEED`, `GEAR_SELECTION` (CAR_SPEED, CAR_POWERTRAIN) | ✅ |
| 배터리 % (EV) | Vehicle `EvBattery.registerEvBatteryStateOfCharge` | ✅ 실시간 |
| 연료 % (내연기관) | Vehicle `Fuel.getFuelPercent` / `registerFuelPercent` (`CAR_ENERGY`, 승인 불필요) 또는 AAOS `FUEL_LEVEL ÷ INFO_FUEL_CAPACITY` | ⚠️ API 존재 확인, EV 에뮬에선 `NOT_SUPPORTED` → 실값 검증 불가 |
| 차종 판별 | AAOS `INFO_FUEL_TYPE` (10=ELECTRIC) | ✅ |
| 경로 재탐색 / 목적지 변경 / 경유지 추가 | NaviHelper `onRouteStarted`, `onWaypointChanged`, `onRouteCancelled` | ✅ |
| 도착 | `onDestinationArrived` | 📄 (위치 고정으로 에뮬 검증 불가) |
| 연결 끊김 | `lastSeen` 하트비트(5초) 15초 미갱신 시 표시 + `onDisconnect`(정상 종료 시) | ✅ (1-6, `onDisconnect`만으로는 120초 지연) |
| 긴급("충돌 감지") | ❓ 충돌 감지 데이터 출처 미확인. 비상등은 읽기 불가(1-5) | ❓ 아래 참고 |

### 카드 상태 (Figma `member_card · 상태별 예시`)
`status` 값을 그대로 DB에 저장한다. 상태가 바뀐 시각(`statusAt`)도 함께 저장("n분 전" 표시용).

| 상태 | type / status | 판단 근거 |
|---|---|---|
| 이동중 | default / `moving` | 속도 > 0 또는 기어 D·R |
| 정차중 | default / `stopped` | 속도 0 + 일정 시간 유지(예: 30초) 또는 기어 P |
| 도착 | default / `arrived` | `onDestinationArrived` 또는 목적지 반경 300m 안에서 P단 |
| 경로 재탐색 | default / `route_changed` | `onRouteCancelled` → 같은 목적지로 `onRouteStarted` |
| 목적지 변경 | default / `destination_changed` | 다른 목적지로 `onRouteStarted` |
| 경유지 추가 | default / `waypoint_added` | `onWaypointChanged(ADD)` |
| 충전 필요 | default / `energy_low_ev` | SOC ≤ 임계값 (6장) |
| 주유 필요 | default / `energy_low_fuel` | 연료 % ≤ 임계값 (6장) |
| 긴급 | emergency / `emergency` | ❓ 데이터 출처 없음 |
| 연결 끊김 | offline / `offline` | `lastSeen` 15초 미갱신 (받는 쪽에서 판단) |
| 참여 전 | pending / `not_joined` | 초대만 되고 아직 참여 안 함 |

- 경로 재탐색·목적지 변경·경유지 추가·충전/주유 필요는 **카드 문구는 이동중과 같고 칩으로만 알림**. 칩 유지 시간은 구현하면서 정함(예: 1분, 충전/주유 필요는 해소될 때까지).
- 음성메시지 수신 중에는 해당 카드에 파형 표시 (4장).

**문구 규칙 (Figma)**
1. 큰 글씨 — 가는 중이면 **도착 예정 시각**(3:40 PM). 끝났거나 멈춘 상태(도착·긴급·연결 끊김)는 **"무슨 일 · n분 전"**(목적지 도착 · 5분 전)
2. 작은 글씨 — 남은 거리 하나만(162km 남음), **달리고 있을 때만**
3. 위치 — 항상 오른쪽. 도착은 도착한 장소, 연결 끊김은 마지막 위치
4. 하단 줄 — 내가 할 행동이 있을 때만. 왼쪽은 판단 근거, 버튼은 "~하기"
5. 참여 전 — 시간·위치 없이 "초대 수락 대기 중" 한 줄
6. 모든 문구는 명사형, 카드 한 장 최대 3줄

### 제한 사항
- ❌ **비상등 읽기 불가**: AAOS `CAR_EXTERIOR_LIGHTS`가 `signature|privileged`(시스템 앱 전용), Pleos SDK에 공개 API 없음. 콘솔에서 켜도 방향지시등·경고등에 안 잡힘. (11/12 재확인, 1-5)
- 경고등(Telltales)은 `PRIVATE_CAR_SAFETY` 권한으로 읽힘(✅) — 단 앱마켓 승인 필요 권한. **1회 조회(`getTelltalesInfo`)도 PRIVATE 권한 없이는 실패** (11/12 실측)
- **차종 분기 규칙**: `INFO_FUEL_TYPE` 먼저 확인 → `ELECTRIC(10)`이면 EvBattery SOC, 그 외면 `Fuel.checkFuelPercentCapabilities` 지원 시 Pleos `Fuel`, 아니면 AAOS `FUEL_LEVEL ÷ INFO_FUEL_CAPACITY`. **EV에서 반환되는 `FUEL_LEVEL`(15000 = 용량)은 더미값이므로 무시**

### 정책 결정 필요
- [ ] **긴급 상태**: 충돌 감지 데이터 출처 확인(Pleos 기술지원 문의) 전까지 1차는 **봇으로만 시연** vs 제외
- [ ] 위치 공유 범위: 여행(방) 진행 중에만 공유, 종료 시 자동 중단 (개인정보 동의 문구 포함)

## 4. 기본 기능 B — 그룹 음성메시지

### 화면 흐름 (Figma)
- [메시지 남기기] 탭 → 버튼이 **"메시지 남기는 중"**으로 바뀌고, 하단 버튼 위에 **말한 내용이 실시간 텍스트 말풍선**으로 표시
- 전송 완료 → 토스트 **"그룹에게 메시지를 전달했어요."**
- 수신 → 보낸 멤버 카드에 **음성 파형 표시** + 하단에 말풍선(보낸 사람 아바타 + 텍스트)

### 구현 방식 (녹음 1회로 원음 + 텍스트)
1. [메시지 남기기] **탭 1회로 시작 + 무음 감지 시 자동 종료**(누르고 있을 필요 없음). **Android `AudioRecord`(16kHz mono PCM)** 로 녹음 — ✅ 녹음 파이프라인 동작 확인
2. 같은 PCM을 **STT `sendAudio()`(ON_DEVICE)** 에 실시간으로 넣어 말풍선 텍스트 생성 — ✅ 한국어 인식 확인("휴게소 좀 잠깐 들르게 올 거면 와")
   - ❓ **녹음 중 실시간 말풍선은 STT 중간 결과(partial) 콜백이 필요** — 지원 여부 확인. 없으면 녹음 중엔 "메시지 남기는 중"만 표시하고 종료 후 텍스트 표시
3. 원음을 AAC로 인코딩 → **base64로 Realtime DB에 저장** + 텍스트 → `messages`에 기록 — ✅ 80KB 쓰기 0.65초 (1-6). Storage는 버킷 미생성·요금제 문제로 데모에선 사용 안 함
4. 수신 차량: 원음 자동 재생(MediaPlayer, 오디오 포커스 `GAIN_TRANSIENT_MAY_DUCK`) + 파형·말풍선 표시
5. 시스템 안내("○○님이 경유지를 제안했어요")는 **TTS(ON_DEVICE)** — ✅ 백그라운드 재생 확인 (5-5)

### 필요 SDK / 권한
- `RECORD_AUDIO`, SpeechToText 3.3.1(`STT_SERVICE`), TextToSpeech 3.3.1(`TTS_SERVICE`)
- ON_DEVICE 모드는 앱 등록(Client ID/Secret) 불필요

### 제한 사항
- ❌ 스티어링 휠 버튼 PTT(누르는 동안 말하기): 휠 버튼 입력 API 없음. 휠 음성 버튼은 **시스템 음성비서 Gleo가 가져감**(11/12 실측, 1-5). 휠 미디어 키는 앱 포그라운드일 때만 들어오고 음악 앱 조작을 가로채게 되므로 사용 안 함
  - **대체**: 탭 1회 시작 + 무음 자동 종료, 하단 대형 고정 버튼, 동승자 입력
  - 기획서 표현: "휠 버튼 불가"보다 "버튼 없이 말로 답하는 흐름"으로 서술
- ⚠️ 에뮬 실마이크 입력: macOS 마이크 권한 필요 (Extended Controls → Microphone "Virtual microphone uses host audio input" ON) — **재검증 남음**
- ⚠️ 통화 중: Telephony API 제한 → 오디오 포커스 상실(CALL) 시 재생 일시정지로 처리
- TTS 앞음절 잘림 방지: 선행 묵음 적용 가이드 준수(📄)

### 정책 결정 필요
- [ ] 최대 녹음 길이 (기존 와이어프레임: 15초)
- [ ] 멤버 상세 화면의 [메시지 남기기]가 **해당 멤버에게만** 보내는 것인지 (기획: "특정 차량에만 음성 전달") — Figma 확인
- [ ] 원음 보관 기간 (여행 종료 시 삭제 권장)

## 5. Flow 1 — 다같이 경로 변경

하위 기능 4개: **목적지 변경 제안하기 / 여기로 가기 / 같이 들르기 / 중간에 모이기**

### 5-0. 목적지·경유지 관리 원칙 (모든 하위 기능 공통)

**서버가 각 차량의 목적지·경유지(최대 2개, 좌표 포함)를 갖고 있고, 내비에는 항상 "결정된 전체 경로"를 다시 보낸다.**

1. 서버 `members/{uid}/nav`에 목적지 + 경유지 슬롯 1·2 보관 (9-1)
2. 새 경유지가 들어오면:
   - 슬롯이 비어 있으면 추가
   - 2개가 꽉 찼으면 **교체 시트**로 어느 것을 바꿀지 결정받음 (5-3)
3. 결정된 목적지 + 경유지 2개를 **`requestRouteWithWaypoints()`** 로 내비에 한 번에 설정 — ✅
   - 목적지 변경 시에도 같은 API로 보내 **기존 경유지 유지** (`requestRoute` 단독 호출 시 기존 경유지가 모두 삭제됨)
   - 경유지 순서: 사용자의 선택(넣은 순서·교체한 자리)을 따른다. 경유지 1이 경유지 2보다 멀면(되돌아오는 경로) 보내기 전에 사용자에게 확인 (`requestTrip` 거리 비교, 11/15 결정 · 미구현)
4. **내비에서 사용자가 직접 바꾼 내용도 서버에 반영**: `onRouteStarted` / `onWaypointChanged` 수신 → `getDestinationInfo` + 경유지 정보로 서버 갱신
5. **자기 요청 구분**: 우리 앱이 보낸 요청도 `onRouteStarted`·`onRouteCancelled`·`onWaypointChanged`를 받으므로, 요청 직후 N초는 사용자 변경으로 보지 않는 플래그 필요

⚠️ **`getWaypointInfo`로 받은 경유지는 좌표가 항상 0.0** (내비 원본 JSON부터 0). 내비에서 직접 넣은 경유지뿐 아니라 **우리 앱이 좌표를 넣어 보낸 경유지도 0.0으로 돌아옴** (11/15 실측)
- 우리 앱이 넣은 경유지는 보낼 때의 좌표를 앱(`RouteManager`)·서버가 들고 있으므로 문제 없음. 내비 조회값으로 좌표를 덮어쓰지 않는다
- 사용자가 내비에서 직접 넣은 경유지는 `onWaypointChanged` 수신 시 **이름·주소로 지오코딩(카카오 로컬 키워드 검색)해 좌표를 채워 둠**
- 지오코딩 실패 시 그 경유지는 재설정할 때 유지할 수 없음 → 토스트로 "○○ 경유지는 다시 넣어야 해요" 안내

### 5-1. 목적지 변경 제안하기

**보내는 쪽 (내비에서 목적지를 바꾼 차량)** — 하단 시트
- "내비에서 목적지가 바뀌었어요" + 장소 카드(이름 · 거리 · 주소) + "멤버들과 함께 갈까요?"
- [혼자 가기 ⑤] [목적지 제안하기] — 만료 시 혼자 가기
- **혼자 가기를 눌러도 내 목적지는 그룹에 공유됨** → 목적지 그룹이 "강릉순두부장칼국수 · 1대(내 목적지) / 경포해수욕장 · 2대 [여기로 가기]"로 나뉨

**받는 쪽** — 하단 시트
- "{이름}가 목적지를 제안했어요" + 장소 카드 + "{이름}와 함께 갈까요?"
- [그대로 가기 ⑤] [목적지 변경하기] — 수락 시 5-0 방식으로 내비 반영(내 경유지 유지)
- 놓친 제안은 목적지 그룹의 [여기로 가기]로 나중에 따라갈 수 있음 (별도 재알림 없음)

| 단계 | 구현 | 상태 |
|---|---|---|
| 내비 UI에서 바꾼 목적지 감지 | `onRouteCancelled` → **`onRouteStarted`** 수신 후 `getDestinationInfo`로 이름·좌표 획득. ⚠️ 경유지가 있으면 `RouteStartInfo`의 `name`·`distance`는 **첫 경유지 기준**이라 목적지 판단에 쓰지 않음 (11/15 실측) | ✅ (FGS 켠 상태에서 약 5초 내 실시간) |
| 보조 감지 | 앱 포그라운드 복귀 시 `getDestinationInfo` 1회 비교 | 권장 |
| 장소 카드 주소 | ❓ `DestinationInfo`에 주소 필드가 있는지 확인. 없으면 카카오 로컬 `coord2address` | ❓ |
| 장소 카드 거리 | 내 위치 기준 `requestTrip` distance (또는 `remainDistance`) | ✅ |
| 다른 차량에 반영 | `requestRouteWithWaypoints(목적지, 내 경유지)` — poiId 없어도 동작 | ✅ (주행 중에도 OK) |

⚠️ `onDestinationChanged`는 SDK에 정의돼 있으나 에뮬 내비(3.3.2)는 **보내지 않음** → `onRouteStarted`를 변경 신호로 사용

⚠️ 내비 이벤트 실측 (11/15, `requestRouteWithWaypoints` 기준)
- 요청 후 `onRouteStarted`까지 **약 8초**
- `onRouteStarted` **직후 `onRouteEnded`가 바로 옴** → 종료·취소 이벤트를 받아도 상태를 바로 비우지 말고 `getDestinationInfo`로 다시 확인
- 경로가 없을 때 `getDestinationInfo`는 오류 대신 **이름 `""`·좌표 0.0인 빈 값**을 줌 → 이걸 "경로 없음"으로 판단

### 5-2. 여기로 가기 (그룹 내 목적지가 갈렸을 때)
- 서버의 차량별 목적지로 그룹핑("경포해수욕장 · 2대 / 강릉역 KTX · 1대"). 같은 목적지 판단은 좌표 근접(예: 200m 이내) 또는 이름 일치
- 다른 그룹의 [여기로 가기] → 하단 시트 "해당 목적지로 변경할까요?" + 장소 카드 → [그대로 가기 ⑤] [목적지 변경하기]
- 수락 시 5-0 방식(기존 경유지 유지) — ✅

### 5-3. 같이 들르기 (멤버의 경유지에 합류)

**진입: 멤버 카드 탭 → "{이름} 정보" 상세 화면**
- 상단: 멤버 요약(이름 · 배터리 · 상태) + [중간에 모이기] [메시지 남기기]
- "{이름}의 경로" + 오른쪽에 **"내 경유지 n/2"**
- 타임라인: 현재 위치 → 경유지 1 → 경유지 2 → 목적지
  - 각 지점: 이름, **"{이름} 2:10 PM 도착"**(그 멤버의 도착 예정 시각), **"여기서 32km"**(내 위치 기준 거리)
  - 경유지 버튼: [같이 들르기] → 추가 후 "경유지에 추가됨"
  - 목적지: 같으면 "나와 같은 목적지", 다르면 [여기로 가기]

**[같이 들르기] 동작**
- 내 경유지가 2개 미만 → 추가(5-0) → 토스트 **"경유지가 추가됐어요."**
- 2개가 꽉 참 → **교체 시트**: "경유지는 2곳까지 넣을 수 있어요" + 새 경유지 카드("{이름}의 경유지 · 2:23 PM 도착") + "기존 경유지와 교체할까요?" + 내 경유지 1·2 목록(도착 시각 · 거리, 각각 [교체]) + [그대로 가기 ⑤]
- 교체 결정 후 남은 2개를 `requestRouteWithWaypoints`로 내비에 반영 (5-0)

| 데이터 | 출처 | 상태 |
|---|---|---|
| 멤버 경유지 목록·순서 | 멤버 앱이 서버 `nav.waypoints`에 업로드 | ✅ |
| 멤버의 경유지별 도착 시각 | 멤버 앱이 내비 경유지 남은 시간(`onWayPointInfo`/`DrivingInfo`)으로 계산해 업로드 | ✅ |
| "여기서 Nkm" | 내 위치 → 경유지 좌표 거리. `requestTrip` distance 권장(직선거리로 대체 가능) | ✅ (좌표는 5-0 지오코딩 전제) |
| 내 경유지 도착 시각·거리(교체 시트) | 내 내비 경유지 정보 | ✅ |

⚠️ 제약
- **경유지 최대 2개**(FIRST/SECOND). `addWaypoint`로 FIRST에 추가 시 기존 FIRST→SECOND, 기존 SECOND 삭제됨 ✅ 실측 → 그래서 `addWaypoint` 대신 5-0의 전체 재설정 방식을 씀
- 경로 재설정 순간 `onRouteCancelled`가 잠깐 옴 → 자기 요청 플래그로 무시

### 5-4. 중간에 모이기

**제안하는 쪽** — [중간에 모이기] → 하단 시트
- "어디서 모일까요?" / "멤버들과 모이기 좋은 경유지 장소예요"
- 탭: **휴게소 / 카페 / 음식점**
- 추천 카드: 유형 라벨(**동시 도착 / 중간 지점 / 최소 우회**) + "추천" 배지 + 장소 이름 + 편의시설 태그(충전소·식당·편의점) + **"15분 뒤 모두 도착 · 대기 최대 4분"**
- [뒤로가기] [경유지 제안하기] — 카드 수는 Figma 최종안을 따름(2~3개)
- 제안하면 내 경로에도 해당 경유지 추가(5-0)

**받는 쪽** — 하단 시트
- "{이름}가 중간에 모이기를 제안했어요" + 장소 카드("28분 뒤 모두 도착 · 대기 최대 12분") + "경유지를 추가할까요?"
- [그대로 가기 ⑤] [경유지 추가하기] — 수락 시 5-0 방식(꽉 찼으면 교체 시트)
- 놓친 제안은 제안자 상세 화면의 [같이 들르기]로 나중에 추가 가능

| 단계 | 구현 | 상태 |
|---|---|---|
| 후보지 목록 | **외부 데이터 필요** — NaviHelper에 POI 검색 API 없음. 휴게소: 고속도로 휴게소 공공데이터(앱 내장, 편의시설·전기차 충전소 포함). 카페·음식점: 카카오 로컬 카테고리 검색(`CE7`, `FD6`) | 자체 로직 |
| 후보 범위 | 그룹 차량들의 현재 위치 ~ 목적지 사이, 맨 앞차보다 앞쪽 경로 주변 | 자체 로직 |
| 차량별 후보지 도착시간 | 각 차량이 **`requestTrip(TripRequest)`** → `onTripInfo(eta 초, distance m, estimatedSocAtDest %)` 를 서버에 업로드 (9-1 `meetups`) | ✅ 현재 경로 변경 없음, 3곳 동시 요청 OK, `routePoints.poiName`으로 응답 구분 |
| 추천 점수 | 제안하는 차량 앱에서 계산: 동시 도착 = ETA 편차 최소, 대기 최대 = max−min, 중간 지점 = 차량 간 거리 중간, 우회 = (ETA_후보+후보→목적지) − 원래 ETA | 자체 로직 |
| 가상 차량 ETA | 봇은 직선거리·평균속도로 근사해 업로드 | 자체 로직 |

**이 추천 엔진은 Flow 2에서 그대로 재사용** (6장)

### 5-5. 선택 확장: TTS 안내 + 음성 수락 (Figma에 화면 없음, 시간 되면)
- 제안 도착 시 **TTS로 한 번 읽어 줌**("언니네가 목적지를 제안했어요"). 화면 요소가 아니라 Figma와 충돌 없음
- **음성 수락은 Flow 2 제안(15초)에만** 적용. Flow 1 시트는 5초라 TTS + 듣기 시간이 부족함
  1. TTS 끝에 "같이 쉬어갈까요?"
  2. TTS가 끝나면 STT를 약 5초 켜고 🎙 표시
  3. 키워드만 판단: 수락("응/좋아/그래/가자"), 거절("아니/그대로/됐어"), 그 외는 무시하고 터치 대기
  4. 음성으로 수락했을 때만 토스트에 [되돌리기] (오인식 안전장치)
- STT 한국어 인식은 실측 확인됨(4장) → 심사 "차량특화성" 근거로 활용 가능
- 휠 버튼·Gleo 연동은 불가/제외 (1-5)

## 6. Flow 2 — 차량 상태 기반 그룹 합류 지점 제안

> Figma `Wireframe/Flow 2`는 작업 중. 문구·화면은 최신 Figma를 따름.

### 화면 (Figma)
- **패널 상단 고정 카드** (모달 아님. 아래 목적지 그룹·멤버 카드는 그대로 보임)
  - 라벨 "경유지 제안" (나에게만 보내는 경우 "나에게만")
  - **응답 현황 "2/3 수락" + 멤버 아바타** (모두에게 보내는 경우, 제안 차량 포함)
  - 제안 문구 + 장소 카드("횡성휴게소 (강릉 방향) · 28분 뒤 모두 도착 · 대기 최대 12분")
  - [그대로 가기 ⑮] [경유지 추가하기 (k/2)] — k = 현재 내 경유지 수
- 수락 → 토스트 **"경유지를 추가했어요."** (경유지 반영은 5-0)
- 트리거 차량의 멤버 카드에 상태 칩(충전 필요 등)

### 트리거
| 트리거 | 대상 | 문구 (Figma) | 데이터 | 상태 |
|---|---|---|---|---|
| 배터리 부족 (EV) | 모두에게 | "{이름} 차량 충전이 필요해요. 같이 쉬어갈까요?" | `EvBattery` SOC 구독, 또는 `onTripInfo.estimatedSocAtDest` / `RouteStateInfo.remainDestinationChargingInt` (도착 시 예상 잔량) | ✅ 콘솔로 15% 설정 시 즉시 수신 |
| 연료 부족 (내연기관) | 모두에게 | 배터리와 같은 형식("주유가 필요해요") | `Fuel.registerFuelPercent` (`CAR_ENERGY`) / AAOS `FUEL_LEVEL`, `FUEL_LEVEL_LOW` | ⚠️ EV 에뮬에선 미지원 → **봇으로 시연** |
| 장시간 운전 | 모두에게 | "2시간째 운전 중이에요. 같이 쉬어갈까요?" | 앱 내 주행 시간 누적(기어 D 기준, 일정 시간 이상 정차 시 초기화) | ✅ (시연은 임계값을 낮추거나 봇으로) |
| 앞·뒤차 간격 벌어짐 | **나에게만** (앞차) | "뒤차 {이름}와 32분 차이 나요. 여기서 기다릴까요?" | 앞차 앱이 같은 목적지 멤버들과 ETA 차이 계산 | 자체 로직 |
| 재합류 | — | (Figma 화면 없음) | 개별 이동 멤버가 다시 출발 시 | 디자인 나오면 |
| 경고등 | — | — | Telltales `LOW_EV_BATTERY`, `LOW_FUEL` (`PRIVATE_CAR_SAFETY`) | ⚠️ **조회도 승인 권한 필요**(11/12) → 확장 |

### 구현 방식
1. **트리거를 감지한 차량의 앱이 제안을 만듦** (배터리·연료·장시간 = 해당 차량, 간격 = 앞차)
2. 후보 장소 목록 → 각 차량 `requestTrip`으로 ETA 수집 → **5-4 추천 엔진 재사용** → 1순위 장소로 제안 생성(`proposals`, 9-1)
3. 받는 차량은 상단 카드 표시(+ 선택 시 TTS, 5-5) → 응답을 `responses/{uid}`에 기록 → 모든 카드의 "n/m 수락"이 실시간 갱신
4. 수락 시 5-0 방식으로 경유지 반영

### 제한 사항
- 판단 규칙은 **규칙 기반**(LLM SDK는 에뮬 v2.1.0부터 제공 종료 ❌)
- 와이퍼 상태(비 오는 구간 알림)는 Pleos `Wiper`(CAR_WINDOWS)로 읽기 가능 📄, AAOS 표준은 시스템 전용 → 1차 제외
- 블랙아이스·침수 등 위험 알림은 데이터 근거 약함 → 1차 제외

### 정책 결정 필요
- [ ] 임계값 (기본값으로 시작): 배터리 ≤20%(또는 도착 시 예상 ≤10%), 차량 간격 ≥10분, 연속 운전 ≥2시간
- [ ] 같은 트리거 재알림 간격(스팸 방지, 예: 20분)
- [ ] 경고등 권한(`PRIVATE_CAR_SAFETY`) 사용 여부 — 앱마켓 승인 필요(조회 포함)하므로 기획서엔 "확장" 표기 권장

## 7. Flow 3 — 주차 자리 안내 (여유 시)

> 목적지 주차장 빈자리가 그룹 차량 수보다 적으면 차량별로 주차장을 나눠 안내. **공영주차장 실시간 API와 멤버 제보를 함께 사용** (주차장 데이터가 적다는 피드백으로 제보 방식 추가). Figma `Wireframe/Flow 3`는 작업 중.

### A. 공영주차장 API가 있을 때
- 목적지에 가까워지면 빈자리 확인 → "주차장 빈자리가 1면뿐이에요" 안내
- 먼저 도착하는 차량(ETA 순)에 빈자리 배정, 나머지는 가까운 주차장(빈자리 n면)으로 **목적지 변경 제안** → 수락한 차량만 5-0 방식으로 반영

### B. 멤버 제보 (API 정보가 없는 주차장)
| 단계 | 내용 (Figma 로직) | 데이터 |
|---|---|---|
| 1. 주차 감지 | 목적지 반경 300m 안에서 **P단 + 정차** → "주차함". 시동 끄기 전이라 화면으로 바로 물어봄 | `GEAR_SELECTION`, 속도, FusedLocation ✅ |
| 2. 주차장 이름 | P단 순간 좌표를 **전국주차장정보 표준데이터** 좌표와 매칭. 없으면 "목적지 근처" | 공공데이터(앱 내장) |
| 3. 질문 | "주차했어요. 다른 멤버가 댈 자리도 있나요?" [자리 있어요] [자리 부족해요] + ⑮ X. **X·15초 무응답이면 판단 없이 자동 정보만 공유** | — |
| 4. 전달 시점 | 제보 직후: 나머지 멤버는 토스트 + 멤버 카드 상태만 바뀜(끼어들지 않음). **판단이 필요한 알림은 각 멤버가 목적지 2km 전에 도착할 때** 제보 시각과 함께. 30분 지난 제보는 안 씀 | `remainDistance` ✅ |
| 5. 받는 쪽 선택 | 자리 있어요 → "부모님이 주차한 곳으로 갈까요?" / X·무응답 → 같은 제안, 주차 시각·걸린 시간만 표시 / 자리 부족해요 → 부족한 주차장은 흐리게, 대신 갈 주차장 제안 / 수락 → 토스트 후 내비 안내 | NaviHelper ✅ |
| 자리 찾는 중 | 안내 종료 후 3분 넘게 P단 없이 반경 안을 저속 이동 → "주차 자리 찾는 중". 첫 차에 근처 주차장으로 목적지 변경 제안, 그룹엔 카드 상태만 변경 | 자체 로직 |

### 필요 데이터 / API
- 공공데이터: 서울시 공영주차장 실시간, 한국교통안전공단 주차정보 API(일부 실시간), 공항 주차장 등 — **공영 노외주차장 위주**
- 전국주차장정보 표준데이터 (주차장 좌표·이름 매칭용)
- 민영·상가·아파트 주차장은 제휴 없이는 데이터 없음 → 제보로 보완
- 데이터 출처 API 키 발급·호출 제한 확인 필요

### 정책 결정 필요
- [ ] "자리 찾는 중" 판단 기준 (Figma 임시값: 3분, 반경 300m)
- [ ] 시연 장소(경포해수욕장 등)에 실데이터가 없으면 목업 데이터 사용
- [ ] 기획서 표현: "실 출시 시 지자체·주차 플랫폼 제휴로 확장" 로드맵

## 9. 개발 준비 (초기 세팅 전 참고)

### 9-1. Realtime DB 구조 (초안)
```
codes/{참여코드}: roomId

rooms/{roomId}/
  meta: { name, code, createdBy, createdAt, status: active|ended }
  members/{uid}/
    profile:  { name, initial, color, fuelType: ev|fuel }
    joinState: invited|joined
    status:   moving|stopped|arrived|route_changed|destination_changed|waypoint_added
              |energy_low_ev|energy_low_fuel|emergency|not_joined     ← offline은 lastSeen으로 받는 쪽이 판단
    statusAt: epoch ms
    nav/
      dest:      { name, lat, lon, address }
      waypoints: { 1: {name, lat, lon, address, etaAt, source: app|navi}, 2: {...} }   ← lat/lon null = 지오코딩 실패
      etaAt, remainDistM, totalDistM          ← 진행 바 = 1 − remain/total
    vehicle:  { soc, fuelPct, gear, speedKmh, driveStartAt }
    location: { lat, lon, label, at }
    online, lastSeen
  proposals/{pid}/
    { kind: destination|meetup|flow2, trigger: low_ev|low_fuel|long_drive|gap|null,
      from: uid, to: all|{uid}, place: {name, lat, lon, address, tags},
      summary: { allArriveMin, maxWaitMin }, createdAt, expiresAt,
      status: open|cancelled|replaced|done }
    responses/{uid}: { answer: accepted|declined|pending, at }
  meetups/{mid}/                                ← 중간에 모이기·Flow 2 추천 계산용
    { from: uid, candidates: [{poiId, name, lat, lon, tags}], createdAt }
    etas/{uid}/{poiId}: { etaSec, distM, socAtDest }
  messages/{msgId}: { from: uid, to: all|uid, text, audioB64, durMs, createdAt }
```
- 같은 사람의 새 제안은 이전 `open` 제안을 `replaced`로 바꿈
- 여행 종료(`meta.status=ended`) 시 `messages` 삭제, 위치 공유 중단

### 9-2. 제안(proposal) 처리 흐름
1. 제안자 앱이 `proposals/{pid}` 생성 (`expiresAt` = 지금 + 5초(Flow 1) / 15초(Flow 2))
2. 받는 앱: 리스너로 수신 → 시트/카드 표시 + 카운트다운 → 응답을 `responses/{uid}`에 기록
3. 수락한 앱은 **자기 내비에 직접 반영** (5-0). 서버나 다른 차량이 대신 경로를 바꾸지 않음
4. 만료는 각 앱이 로컬 시계로 처리 (응답 없으면 `pending` 그대로 → 거절과 같은 의미)

### 9-3. 가상 차량 봇 (맥 REST 스크립트)
Flow 1·2 시연에 필요한 동작을 명령 단위로 준비:

| 명령 | 동작 | 쓰이는 장면 |
|---|---|---|
| `join` | 방에 멤버로 참여(익명 토큰) | 시작 |
| `drive` | 경로 좌표를 따라 이동, `location`·`etaAt`·`remainDistM` 갱신 | 상시 |
| `dest <장소>` | 목적지 변경 + `destination_changed` | 여기로 가기 |
| `propose-dest <장소>` | 목적지 변경 제안 생성 | 5-1 받는 쪽 |
| `add-wp <장소>` | 경유지 추가 + `waypoint_added` | 같이 들르기 |
| `meetup <장소>` | 중간에 모이기 제안 생성 | 5-4 받는 쪽 |
| `respond <pid> accept\|decline` | 제안에 응답(지연 시간 지정 가능) | n/m 수락 표시 |
| `soc <n>` / `fuel <n>` | 배터리·연료 값 변경 → 임계값 이하면 Flow 2 제안 생성 | Flow 2 충전/주유 |
| `long-drive` | 주행 시작 시각을 과거로 설정 | Flow 2 장시간 운전 |
| `lag <분>` | ETA를 늦춰 차량 간격 벌리기 | Flow 2 간격 |
| `offline` / `online` | 하트비트 중단·재개 | 연결 끊김 |
| `etas` | `meetups` 요청에 직선거리·평균속도 근사 ETA 업로드 | 중간에 모이기 추천 |
| `say <텍스트>` | 음성메시지(미리 녹음한 파일 + 텍스트) 전송 | 음성 수신 |

### 9-4. 프로젝트 골격
- 패키지명: `com.galrae.app` (스파이크는 `com.spike.pleos`)
- SDK: minSdk 28 / targetSdk 34 (스파이크 기준), portrait, `android.hardware.type.automotive` required
- UI: ❓ Jetpack Compose 권장 (카드·시트·토스트 위주 단일 화면)

### 9-5. 온보딩·방 흐름 (데모용 최소 구성, 최종 와이어프레임 없음)
기획 IA(진입 → 프로필·차량 등록 → 방 생성·참여 → 이동 경로 입력 → 그룹 주행 메인)를 데모에 맞게 줄임:
1. 앱 실행 → 익명 로그인(자동)
2. 프로필: 이름 입력(또는 자동 생성), 연료 타입은 `INFO_FUEL_TYPE`으로 자동
3. **방 만들기**(방 이름) → 참여 코드 생성 / **코드로 참여**
4. 위치 권한 요청 → 허용 시 FGS 시작 (1-7)
5. 메인(2장). **목적지는 별도 입력 없이 내비에 설정된 목적지를 읽음**
- 헤더 [+] = 참여 코드 표시(초대). 초대만 하고 아직 안 들어온 멤버는 "참여 전"
- [⋯] → 그룹 나가기 / 여행 종료 → FGS 중지, 위치 공유 중단
- 일회성 방만 지원 (유지형·리더 모드 제외)
